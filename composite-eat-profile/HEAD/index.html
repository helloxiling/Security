Compliance with OCP Tenets

Openness

This profile uses publicly specified evidence formats and enables interoperable verification across platform and device vendors.

Efficiency

This profile combines platform and device evidence into one artifact while preserving native device evidence, reducing repeated external collection and format-conversion operations.

Impact

This profile provides a common method for conveying platform inventory attestation evidence from heterogeneous devices.

Scale

This profile supports flat and recursive platform composition and uses detached evidence to accommodate platforms containing multiple independently attesting devices.

Sustainability

This profile reuses existing EAT, CWT, COSE, CMW, and native device evidence formats, enabling incremental adoption without replacing existing device attestation implementations.

Introduction

Problem Statement

Platform attestation today is commonly disaggregated. Where per-device Evidence is retrieved independently, attesting a whole platform requires separate transactions that return independently protected responses. The Verifier must then reconstruct the relationship between those components, the encompassing platform, and the freshness challenge. There is no single signed, platform-scoped artifact that binds a Verifier nonce, the Lead Attester state, and the reported Sub-Attester Evidence set.

Four gaps follow:

  1. No aggregate. The Verifier reassembles the composite system from independent evidence artifacts.
  2. No uniform carriage. Sub-Attesters may expose SPDM signed measurements, emit their own signed EAT, or themselves produce a Composite EAT. A common structure is needed without rewriting the protected native evidence.
  3. Lead Attester overhead. Requiring the Lead Attester to implement every Sub-Attester protocol solely to describe itself increases trusted-computing base size and complexity.
  4. External orchestration. Retrieving and correlating Evidence independently from every component requires repeated externally visible operations and exposes internal topology and transport details to the Verifier.

Approach

A Lead Attester, following the composite-device pattern in Section 3.3 of [1], produces one signed Composite EAT. The token carries the Lead Attester’s measurements and, for every Sub-Attester, a detached-submodule digest that commits to its evidence. Native evidence is preserved and conveyed in CMW Records under CWT claim 299 in detached Claims-Sets within a Detached EAT Bundle (CBOR tag 602, [2]).

The signed digests bind the detached Claims-Sets. Native signatures preserve the provenance of each Sub-Attester Evidence item. Evidence collection and bundle assembly MAY be performed outside the Lead Attester without granting those functions authority to produce or appraise native Evidence.

The resulting bundle provides one platform-scoped artifact for a collection event. The signed main token binds the Lead Attester identity, Lead Attester measurements, freshness challenge, reported Target Environment Identifiers, and digests of the included detached Claims-Sets. This reduces external collection transactions and topology-dependent orchestration while preserving native Evidence provenance. It does not replace native Evidence validation or appraisal against independently trusted expected-composition information.

Scope

This document specifies the Composite EAT evidence format for platform inventory attestation: the signed main token, detached native-Evidence carriage, digest binding, processing rules, and supported Evidence forms. It supports flat and recursive platform composition.

Appraisal against composition endorsements and reference values is described informatively and specified by deployment policy. Transport APIs, physical connector locality, bus-level anti-relay guarantees, trust-anchor enrollment, and endorsement authoring are outside scope.

Workload attestation, tenant attestation, confidential-computing device assignment, and Trusted Device Interface Security Protocol (TDISP) device attachment are outside the scope of this profile.

Conventions and Terminology

The key words “MUST”, “MUST NOT”, “REQUIRED”, “SHALL”, “SHALL NOT”, “SHOULD”, “SHOULD NOT”, “RECOMMENDED”, “NOT RECOMMENDED”, “MAY”, and “OPTIONAL” in this document are to be interpreted as described in BCP 14 [3] [4] when, and only when, they appear in all capitals.

Data structures are defined using the Concise Data Definition Language (CDDL) [5].

This document uses Attester, Verifier, Relying Party, Endorser, Reference Value Provider, Lead Attester, Sub-Attester, Composite Device, Target Environment, and Attesting Environment as defined in [1].

Detached Claims-Set:
The native Sub-Attester evidence for one Target Environment, encoded as a CBOR Claims-Set and conveyed in the detached slot of the Detached EAT Bundle. A digest in the signed Composite EAT commits to it.
Target Environment Identifier:
A stable topology label rendered as an env.* string and used as the map key for a Sub-Attester in both the signed submods claim and detached Claims-Set map.

Architecture and Trust Model

Composite Device Architecture and Trust Boundaries

This profile applies the RFC 9334 composite-device pattern. The Lead Attester constructs and signs the main token, including the nonce, its identity and measurements, the reported Target Environment Identifiers, and the detached Claims-Set digests. The Lead Attester does not appear in submods; its claims are top-level claims.

Sub-Attesters produce independently protected native Evidence. The Lead Attester signature does not make the Lead Attester authoritative for that Evidence. The Verifier validates the Composite EAT signature and each Sub-Attester’s native protection, then appraises the reported composition using independently trusted expected-composition information supplied by an Endorser, Reference Value Provider, or other source authorized by Verifier policy.

In a BMC-mediated implementation, the Lead Attester can be a Root of Trust associated with the BMC. The BMC RoT protects the Composite EAT signing key, supplies the Lead Attester identity and local measurements, and produces the signed main token.

Delegated Collection and Bundle-Assembly Functions

Evidence collection and bundle assembly are implementation functions that MAY be delegated to one or more supporting components, either within or outside the Lead Attester’s protected boundary. These functions may discover Sub-Attesters, obtain native Evidence, construct detached Claims-Sets, and assemble or convey the final bundle. In a BMC-mediated implementation, BMC software commonly performs these functions outside the BMC RoT’s protected signing boundary.

Delegation does not transfer Lead Attester authority. Supporting components may supply the nonce, reported Target Environment Identifiers, and detached Claims-Set digest records as inputs, and may combine the signed main token with the detached Claims-Sets. They cannot produce the Lead Attester signature and are not authoritative for native Evidence authenticity, collection completeness, or Target Environment Identifier correctness.

A collection implementation SHOULD use an authenticated collection policy, or an equivalent trusted mechanism, to mitigate the risk of accidental or malicious omission during Evidence collection. Such hardening improves collection coverage and integrity. It does not establish platform-inventory completeness or make the collection implementation authoritative for expected platform composition.

Security Properties and Limits

The Composite EAT signature establishes integrity and freshness of the included platform observation. It does not independently establish platform-inventory completeness, Target Environment Identifier correctness, physical locality, or protection against bus-level relay. Those properties require Verifier appraisal against independently trusted expected-composition information and, where applicable, additional transport or hardware assurances.

Composite EAT Profile

Profile Identifier

This specification requests assignment of the following object identifier (OID) from the OCP Security branch:

ocp-composite-eat OBJECT IDENTIFIER ::= {1 3 6 1 4 1 42623 1 4}

The requested dotted-decimal value is 1.3.6.1.4.1.42623.1.4. This value is a proposed assignment pending confirmation by OCP and is not assigned or reserved by publication of this working draft. Implementations MUST NOT emit it as an assigned profile identifier until OCP approves the assignment.

After approval, the eat_profile claim (claim 265) MUST contain this OID. In CBOR, it MUST use the preferred PEN-relative encoding with tag 112 defined by [6]. The resulting diagnostic notation is 112(h'82cc7f0104').

The OID 1.3.6.1.4.1.42623.1.3 identifies the OCP Profile for IETF Entity Attestation Token and MUST NOT be used as the profile identifier of the Composite EAT main token. A device-emitted EAT carried as Sub-Attester Evidence MUST conform to the OCP Profile for IETF Entity Attestation Token and identify that profile in its own eat_profile claim. This requirement does not require a Sub-Attester that supplies native SPDM Evidence to emit an EAT.

Conforming producers MUST emit every choice in the table. Conforming Verifiers MUST support those choices. A producer MUST NOT add claims to composite-eat-claims or detached-claims-set beyond those permitted by the closed CDDL maps. A Verifier MUST reject a token or detached Claims-Set containing an additional claim.

This is a full EAT profile in the sense of Section 6.2 of [2]. The classification applies to decoding, verifying, and checking freshness of the Composite EAT envelope. Native Evidence in claim 299 is claim content whose appraisal is governed by its identified format and Verifier policy. A Verifier MUST NOT produce a successful Attestation Result for a native Evidence item unless it can validate that item locally or delegate validation to a trusted Verifier that supports the identified format and algorithms.

Bundle Structure

The authoritative artifact is a Detached EAT Bundle with CBOR tag 602. Slot 1 is the signed Composite EAT (main-token). Slot 2 is the detached Claims-Set map keyed by Target Environment Identifier. When conveyed with a media type, the bundle MUST use application/eat-bun+cbor.

composite-bundle = #6.602([
  main-token: bstr .cbor composite-eat,
  detached-claims-sets: {
    + env-id => bstr .cbor detached-claims-set
  }
])

composite-eat = #6.61(#6.18([
  protected:   bstr .cbor protected-headers,
  unprotected: unprotected-headers,
  payload:     bstr .cbor composite-eat-claims,
  signature:   bstr
]))

protected-headers = {
  1:  -35,
  3:  "application/eat+cwt",
  34: certificate-thumbprint
}

certificate-thumbprint = [ -43, bstr .size 48 ]

unprotected-headers = {
  33: cose-x509-chain
}

cose-x509-chain = bstr / [ 2* bstr ]

Every certificate in cose-x509-chain is DER encoded. A chain containing more than one certificate MUST begin with the Lead Attester end-entity certificate. The protected x5t MUST use SHA-384 and equal the SHA-384 digest of the complete DER encoding of that certificate.

A Verifier MUST reject the token if x5t does not match the first certificate in x5chain. It MUST treat every carried certificate as untrusted input and validate a path to a trust anchor configured independently of the bundle, including applicable certificate usage, validity, and revocation checks [13].

Top-Level Claims

composite-eat-claims = {
  10:  bstr .size 32,
  265: profile-oid,
  256: bstr .size (7..33),
  273: measurements-type,
  266: submods-type
}

The eat_nonce claim contains exactly one nonce. The Verifier MUST generate a new nonce for every request. The same nonce MUST be used to obtain every nonce-capable Sub-Attester evidence item included in the bundle.

Claim 265 MUST equal the OCP Composite EAT profile OID approved before final publication. The requested value is not an assigned profile identifier until OCP approves it.

Lead Attester Self-Measurements

The Lead Attester’s local evidence is carried in top-level claim 273, not in submods.

measurements-type = [ + lead-attester-concise-evidence ]

lead-attester-concise-evidence = [
  content-format: 10571,
  value: bstr .cbor concise-evidence-map
]

This constrains the measurements claim from [2]. Each entry MUST use CoAP Content-Format 10571 (application/ce+cbor) and contain a byte-string-wrapped concise-evidence-map conforming to [14]. This is the same measurement encoding required by the OCP Profile for IETF Entity Attestation Token. The Concise Evidence carried here describes Target Environments measured by the Lead Attester; Sub-Attester Evidence remains detached under submods.

Detached Sub-Attester Evidence

Detached-Submodule-Digest Binding

Every Sub-Attester is represented in the signed token by a Detached-Submodule-Digest. The complete evidence is carried in slot 2 of the bundle under the same Target Environment Identifier.

submods-type = { + env-id => detached-submodule-digest }

detached-submodule-digest = [
  hash-alg: -43,
  digest:   bstr .size 48
]

env-id = tstr .size (5..64)

For every Target Environment Identifier E, submods[E] MUST equal the SHA-384 digest of detached-claims-sets[E] computed according to Deterministic Encoding and Digest Rules. The key set of submods MUST be identical to the key set of detached-claims-sets. A Verifier MUST reject a bundle containing a missing or unreferenced detached Claims-Set.

Deterministic Encoding and Digest Rules

Each detached Claims-Set MUST satisfy the core deterministic encoding requirements of Section 4.2.1 of [7]. A Verifier MUST reject a Claims-Set that does not satisfy those requirements.

The digest input is the encoded Claims-Set bytes directly, not the byte-string wrapper used by the bundle and not a textual encoding. SHA-384, COSE algorithm -43, MUST be used for every detached-submodule digest. This algorithm is independent of a measurement hash negotiated by a native protocol.

Native Evidence Carriage

Each detached Claims-Set contains registered CWT claim 299 (cmw) from [12]. Its value is one CMW Record. The CMW type identifies the native evidence format.

detached-claims-set = {
  299 => native-evidence-cmw
}

native-evidence-cmw = spdm-evidence-cmw /
                      device-eat-cmw /
                      composite-eat-bundle-cmw

Each CMW carries the Evidence conceptual-message indicator. Evidence is bit 2 in the RFC 9999 ind bitmap and is encoded as integer 4. CMW is encapsulation, not security protection. A Verifier MUST validate native protection and provenance after validating the detached digest.

SPDM Signed Measurements

spdm-evidence-cmw = [
  type: "application/spdm-evidence+cbor",
  value: bstr .cbor spdm-evidence,
  ind: 4
]

spdm-evidence = [
  signed-measurements: bstr,
  cert-chain: bstr,
  ? vca: bstr
]

signed-measurements is the binary SPDM SignedMeasurements value. For SPDM 1.2 and later, it includes the negotiated-version, capabilities, and algorithms (VCA) transcript. For SPDM 1.0 and 1.1, it contains only the signed GET_MEASUREMENTS exchange.

cert-chain is the concatenation, in SPDM chain order, of the DER-encoded certificates extracted from the reassembled SPDM certificate chain. It excludes the SPDM Length, Reserved, and RootHash fields and is not PEM encoded.

vca is the observed VCA transcript. It MUST be present for SPDM 1.0 and 1.1 and MUST be absent for SPDM 1.2 and later. See [15].

Device-Emitted EAT

device-eat-cmw = [
  type: "application/eat+cwt",
  device-token: bstr,
  ind: 4
]

device-token MUST contain the complete CWT-encoded EAT as emitted by the device, without decoding or re-encoding. It MUST cryptographically bind the Verifier nonce. It MUST conform to the OCP Profile for IETF Entity Attestation Token and MUST identify that profile in claim 265. Other registered EAT media types require a revision of this profile.

Recursive Composite EAT

A Sub-Attester that is itself a Lead Attester MAY supply a complete Composite EAT bundle as native evidence.

composite-eat-bundle-cmw = [
  type: "application/eat-bun+cbor",
  value: bstr .cbor composite-bundle,
  ind: 4
]

The child bundle MUST conform to this profile and MUST bind the same Verifier nonce as its parent. The Verifier MUST recursively perform the validation in Verification. Implementations SHOULD enforce a deployment-specific maximum nesting depth.

SPDM-Carried TCG DICE Concise Evidence

Signed measurements carrying TCG DICE Concise Evidence [14] use the spdm-evidence-cmw schema. The measurement blocks are preserved verbatim. The component performing collection does not need to distinguish ordinary SPDM measurements from blocks carrying TCG DICE Concise Evidence. The Verifier interprets those blocks under the applicable native Evidence profile.

CMW and Digest Boundaries

The CMW is part of the detached Claims-Set. The digest input therefore includes claim key 299, the complete deterministic CMW encoding, its type and ind fields, and its value byte string.

A conveying protocol MAY additionally carry the complete composite-bundle as a CMW typed value. Such an outer wrapper is not part of a detached Claims-Set digest input.

Target Environment Identifier

The submods key and detached Claims-Set map key is a stable Target Environment Identifier, distinct from transport addresses, device UUIDs, and endorsement identifiers. It:

  1. is lowercase ASCII;
  2. has at least two dot-separated components, with first component env;
  3. names a reported logical environment, not the device instance; and
  4. is between 5 and 64 bytes long.

Examples include env.nic.0, env.gpu.0, and env.pcie.4.

Verification (Informative)

A Verifier is expected to perform the following checks before producing an Attestation Result:

  1. Decode the bundle, confirm tag 602, and enforce every encoding and algorithm choice in Profile Conformance.
  2. Match protected x5t to the end-entity certificate in x5chain, validate the Lead Attester certificate path, and validate the COSE_Sign1 signature.
  3. Match eat_nonce to the challenge, match eat_profile to the approved OCP Composite EAT profile identifier, and validate the Lead Attester ueid and measurements.
  4. Require identical submods and detached Claims-Set key sets and recompute every digest according to Deterministic Encoding and Digest Rules.
  5. Parse each claim-299 CMW, validate its native signature and certificate or token chain, and match its nonce to the challenge.
  6. Match the identity proven by each native Evidence item to the identity authorized for its reported Target Environment Identifier by independently trusted composition information.

The Composite EAT signature, matching key sets, and detached digests establish the integrity and freshness of the included platform observation. Digest validation detects replacement of an included detached Claims-Set, and native Evidence validation establishes its Sub-Attester provenance. Determining whether authentic Evidence is associated with the correct logical environment requires independent appraisal.

A Verifier MUST NOT infer platform-inventory completeness solely from the Composite EAT signature or from agreement between the signed submods map and the detached Claims-Set map. A Verifier that determines platform-inventory completeness MUST compare the reported environment set and proven native identities against independently trusted expected-composition information. A platform CoRIM [16] is one possible source. Native measurements are appraised against trusted reference values selected by Verifier policy. This profile does not define endorsement discovery or reference-value appraisal.

Security Considerations

The security considerations of [17], [9], [11], [2], [12], and [1] apply.

Native Evidence Protection

Native signatures remain end-to-end verifiable because evidence is carried verbatim and pinned by a signed digest. A Verifier MUST validate both layers. Accepting the Composite EAT signature without validating native evidence would incorrectly treat collection-component-authored bytes as Sub-Attester-authored Evidence.

Each native Evidence item MUST independently prove binding to the same nonce. A Verifier MUST reject an item whose nonce is absent, unverifiable, or does not match the challenge.

The fixed ES384 and SHA-384 choices prevent algorithm substitution at the Composite EAT layer. For SPDM 1.0 and 1.1, the separately carried VCA transcript is not covered by the responder’s measurement signature. A deployment requiring cryptographic binding of negotiated SPDM parameters MUST require SPDM 1.2 or later in appraisal policy.

Lead Attester Protection

The Lead Attester signing key and sources of ueid and top-level measurements MUST be protected from untrusted software performing Evidence collection or bundle assembly. The ueid MUST follow [2] and remain stable for the Lead Attester.

Compromise of the Lead Attester signing key permits forgery of the envelope, nonce, Lead Attester measurements, labels, and evidence digests. It does not permit forgery of an uncompromised Sub-Attester signature but defeats the platform-scoped binding. Verifiers MUST validate the Lead Attester certificate path, revocation state, and authorization policy rather than trusting a chain because it is carried in x5chain.

Verifiers MUST perform the certificate-path and protected x5t validation specified in Bundle Structure.

Resource Exhaustion

Detached evidence, certificate chains, recursive bundles, and the number of submodules are attacker-influenced inputs. Implementations SHOULD enforce limits on bundle size, Claims-Set size, certificate-chain length, submodule count, and nesting depth. Verifiers SHOULD validate structure and signed digests before expensive native appraisal, without treating a valid digest as a substitute for native signature validation.

Privacy Considerations

A stable Lead Attester ueid and end-entity certificate enable correlation. Native device certificates and device-emitted EATs can identify individual Sub-Attesters. Target Environment Identifiers expose topology, and measurements can reveal firmware versions or configuration.

Deployments SHOULD restrict bundle access to authorized Verifiers and use a confidentiality-protected conveying protocol when this information is sensitive. A Verifier SHOULD disclose only the Attestation Result needed by a Relying Party rather than forwarding the bundle. Nonces SHOULD be unpredictable and MUST NOT encode user, account, workload, or other identifying information.

IANA Considerations

This OCP specification requests no IANA action. It uses application/spdm-evidence+cbor, whose registration is requested by the aligned IETF Composite EAT specification [18]. The media type identifies the deterministic CBOR encoding of spdm-evidence defined in this document. Until the registration is complete, implementations remain subject to the status of that IETF request.

Alignment and Change Control

This profile adopts the Composite EAT mechanism defined in draft-sun-rats-composite-eat-00 [18] and applies additional constraints for OCP platform inventory attestation. Unless constrained by this specification, the Composite EAT structure and processing rules remain aligned with the IETF specification.

The IETF and OCP specifications define separate full EAT profiles. A token identifies exactly one of them through claim 265; it does not identify both. Conformance to this OCP profile is determined by this specification. In particular, when an OCP Composite EAT carries a device-emitted EAT as Sub-Attester Evidence, that EAT MUST conform to the OCP Profile for IETF Entity Attestation Token. Native SPDM Evidence remains permitted and need not be converted to a device EAT. This OCP profile also constrains the Lead Attester’s claim 273 measurements to the TCG DICE Concise Evidence encoding used by the OCP Profile for IETF Entity Attestation Token.

This specification requests OID 1.3.6.1.4.1.42623.1.4 for the OCP Composite EAT profile. The request follows the existing OCP Security branch and uses the next child value after the documented .2 and .3 assignments. OCP remains the assignment authority and MUST confirm that the requested child value is available before final publication. The OCP Profile for IETF Entity Attestation Token OID, 1.3.6.1.4.1.42623.1.3, identifies a different full EAT profile and cannot be reused for the Composite EAT main token. After OCP approval, the profile CDDL MUST be narrowed to the exact assigned OID encoding. Final publication also depends on registration of application/spdm-evidence+cbor through the aligned IETF work.

Changes to bundle structure, claims, algorithms, native evidence forms, deterministic encoding, digest input, or verification behavior require explicit OCP review. An incompatible change requires a new OCP profile identifier. When the IETF work becomes an RFC, this document SHOULD replace the draft reference with the RFC and document whether any technical differences remain.

Collected CDDL

The following CDDL collects the profile grammar. The external concise-evidence-map type is defined by [14] and is required when validating the collected grammar. profile-oid accepts a PEN-relative OID structure while the requested OID remains pending. After OCP approves the assignment, it MUST be narrowed to the exact assigned OID encoding.

; after approval. This placeholder type MUST NOT be treated as authorization to
; emit an arbitrary PEN-relative OID.
